# req(ems): «Create Action» on a Task nests the action under that task

## Job Story

When I am looking at a task and realise it needs a concrete next physical step,
I want the «Create Action» button on that task to produce an action that already
belongs to it — so the action shows up under the task in every roll-up, and I
never have to wire the parent by hand or, worse, discover weeks later that a
pile of actions is floating with no home.

## Statement (Gherkin)

```gherkin
Scenario: Task target gets the task as parent
  Given an ems__Task with uid <task-uid> in a non-terminal status
  When «Create Action» is applied to that task
  Then the created ems__Action has ems__Effort_parent referencing <task-uid>

Scenario: Project target is unchanged (no regression)
  Given an ems__Project with uid <project-uid>
  When «Create Action» is applied to that project
  Then the created ems__Action has ems__Effort_parent referencing <project-uid>

Scenario: Prototype target still gets no parent
  Given an ems__TaskPrototype
  When «Create Action» is resolved for that prototype
  Then the command is not offered, and no ems__Action whose ems__Effort_parent
       points at the prototype can be produced through it

Scenario: Non-Effort target gets no parent
  Given a target whose class is neither an ems__Effort subclass nor an ems__Area
  When «Create Action» is applied to it
  Then the created ems__Action has no ems__Effort_parent property at all
  And therefore no value outside the range of ems__Effort_parent is written

Scenario: The ontology admits a Task as a parent
  Given the ems TBox after this requirement
  Then exo__Property_range of ems__Effort_parent is ems__Effort
  And SHACL-lite validation of the merged vault reports 0 violations

Scenario: Sibling create-commands are unaffected
  Given the commands «Create task» and «Create project»
  When either is applied to an ems__Task or an ems__Project target
  Then the resulting asset's ems__Effort_parent is exactly what it was before
       this requirement
```

## Non-goals

- No Create-Task→Task binding, and no change to `create-related-task` /
  `create-next-iteration` / `create-action-instance` — scope is «Create Action»
  only (founder decision #3).
- `ems__ParentEffort` is not deprecated.
- The 72 prototype-created parent-less Actions and the one live parent-less
  non-prototype Action are not migrated.
- The engine is not changed. In particular `classRefMatchesAny` keeps matching
  conditions directly and does **not** walk `exo__Class_superClass` — walking it
  would re-introduce the 2026-05-24 prototype defect.
